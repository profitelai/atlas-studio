Purpose

Why this tool exists

You lose time because specs are vague, disconnected, and get re-explained to every agent five times. Atlas Studio is the fix: one screen that interviews you deeply, enforces that every goal is testable, and outputs an agent-ready package — spec, plan, tasks, and agent instructions — so the next app is built fast, correct, and connected to everything else you run.

It is the front door to Atlas. Before speccing anything new, it asks the catalog "do we already have this?" — so we reuse, not rebuild.

The lifecycle

Stages, and what each must produce

Every stage has a gate: it can't be marked complete until its required outputs exist. This is what stops half-baked specs reaching a builder. The order is design-first and MVP-gated — we design the experience and shrink to the smallest testable slice before planning the build (adopted from the AI Product Dev Toolkit).

Principles

The standing rules every project inherits — reuse-first, cheap-model default, quality bar, hard "never" lines. Set once.

→ principles.md (the constitution)

PRD — what & why

Deep branching interview: problem, users, scope, functionality, connections, data, automation, AI, reporting, benchmark, success. Goals must be measurable to pass.

Screens, the screen-to-screen flow, key components, and the empty/loading/error states most builds forget. Fed from the PRD, before any code.

MVP — smallest slice

The riskiest assumption, the 1–3 features that test it, an explicit cut-list, a measurable success signal, and how we'll test it. The discipline against "building a big thing nobody wants."

→ mvp.md · test plan
4

Planning — the how

Stack, architecture, data model, integrations, security controls, build order, technical risks — now informed by the UX and MVP scope.

→ plan.md · design.md
5

Building — the loop

Plan split into small stories, each with a passes flag. An append-only progress log captures learnings (Ralph). Ships until all pass.

→ tasks.json · progress.md

Launching — the gate

Blocking checklist across Quality, Security, SEO/Perf, Legal, and Ops/Atlas. Nothing ships red; unknowns are "pending", never false-green.

→ launch-checklist.md · evidence receipt

Go/no-go sign-off, then Atlas takes over: watch for drift, schedule the competitor benchmark, promote reusable parts to the catalog, email the first health report.

→ go-live.md · Atlas monitoring active

The quality engine

What makes the output trustworthy

These are the mechanisms — mostly borrowed from Loki Mode and Spec Kit — that separate a real spec from a wish-list.

Measurable goals only

Any goal phrased as "fast", "better", "secure", "nice" is flagged and blocked until it carries a number, threshold, or concrete artifact. "Loads under 2s on 4G" passes; "feels snappy" does not.

WHEN…THEN requirements

Behaviours are captured as testable scenarios, so a builder (human or agent) knows exactly what "correct" means and QA can verify it.

# a requirement the builder can actually test WHEN a user submits the form with a missing email THEN show an inline error and do not create the record

Evidence-based done

A Building story flips to done only with proof attached — a passing test name, a diff, a screenshot. Self-reported "done" without evidence stays open.

Honest incompleteness

Unverified items are reported as pending, never silently passed. The export always ends with a "Still open" list of required-but-unanswered items.

Drift handoff

At Go-live the spec is locked; Atlas thereafter reports divergence between the shipped reality and the spec — the same converge idea, made continuous.

The deliverable

The agent-ready bundle — why the next app builds fast

The whole point: Atlas Studio doesn't hand you a document to re-explain. It exports a folder a coding agent consumes directly and starts building.

# exported on demand — the handoff package principles.md # standing rules prd.md # what & why, WHEN…THEN requirements plan.md # stack, architecture, data model tasks.json # stories with passes flags (Ralph loop) AGENTS.md / CLAUDE.md# behaviour contract for the coding agent review-checklist.md # the launch gate the agent must clear memory.md # decisions & context so nothing is re-asked

This bundle is also what gets promoted into the Atlas catalog when the work finishes — so next time it's reused, not rebuilt.

Requirements

Functional

Interview & capture

FR-1The tool presents a staged, single-screen workflow with a stage selector; the user can move freely between stages and edit any answer at any time.
FR-2Each interview question branches conditionally on prior answers (e.g. "uses AI" reveals model/cost questions), so the user is never asked irrelevant questions.
FR-3Every text field accepts voice input (speech-to-text) with graceful fallback to typing where the microphone is unavailable.
FR-4Answers autosave continuously and restore on reopen; the user can reset to a clean project.

Quality enforcement

FR-5The tool flags non-measurable goals and prompts for a number, threshold, or artifact before that item counts as complete.
FR-6Behavioural requirements can be captured as WHEN…THEN scenarios, and the tool encourages this format.
FR-7Each stage has a completion gate; the stage shows incomplete until its required outputs exist. Required-but-missing items surface in a persistent "Still open" list.
FR-8Building stories carry a passes flag with attached evidence; a story cannot be "done" without proof (test name, diff, or screenshot reference).

Build & launch

FR-9The Building stage manages a task list (add/edit/delete, priority, done) and an append-only progress log.
FR-10The Launch stage provides a blocking checklist across Quality, Security, SEO/Performance, Legal/Content, and Ops/Atlas; unknowns are marked pending, not passed.
FR-11The Go-live stage records a go/no-go decision and an Atlas hand-off (watch, benchmark, promote, report).

Output & integration

FR-12The tool exports the full agent-ready bundle (principles, PRD, plan, tasks.json, AGENTS.md/CLAUDE.md, review checklist, memory) as downloadable files.
FR-13Before a new PRD, the tool queries the Atlas catalog for an existing package that already solves it, and surfaces reuse candidates. (needs the Atlas backend)
FR-14On completion, the finished bundle can be promoted into the Atlas catalog as a reusable package + skill. (needs the Atlas backend)

Non-functional

NFR-1Fast & frictionless: the tool runs client-side, loads instantly, and never blocks on a network call for core capture.
NFR-2Private by default: data stays local until the user explicitly exports; no silent uploads.
NFR-3Model-tiered when AI is added: cheap/fast model for routine capture & classification, strong model only for synthesis & build. (backend phase)
NFR-4Theme-aware & accessible: works in light/dark, keyboard-navigable, respects reduced motion.
NFR-5Tool-agnostic output: the bundle works with Claude Code, Cursor, Copilot, or a plain human — no lock-in.
