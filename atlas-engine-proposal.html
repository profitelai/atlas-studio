Summary

What we're building, in a paragraph

You lose time two ways: AI-driven backups and audits miss things on your nested servers, and every reusable feature gets rebuilt from scratch — about five times — because there's no trusted place that says what "complete" looks like.

Atlas is one always-on engine. A cheap robot watches your servers and code, and whenever something new appears — a site, an app, a package — it catalogs it into one git-based map. Your building agents query that map before they build anything, so they reuse what exists instead of rebuilding it. It runs on autopilot, reports only exceptions, and the library compounds every time you use it — which is exactly what makes it sellable.

The problem

Two leaks, same root cause

1
Discovery misses things. Nested folders, subdomains, and apps-inside-apps mean the last backup silently skipped at least three live sites.
2
Reuse fails. Cloning a package you already built always drops a part — a migration, an env var, a policy page — so you rebuild it again and again.

Both come from the same gap: there is no trusted, always-current source of truth for what you run and what you've built. Everything is rediscovered live, which is unreliable and burns tokens.

The shape of it

One engine, two maps

The same discovery engine maps two things — you build the tool once and point it at both.

🗺️ Server inventory

Every place your sites live, enumerated by script — not guessed.

  • Domains, subdomains, document roots
  • Nested apps & sub-folder sites
  • Databases, services, cron, SSL expiry
  • Last-backup status per property

📦 Package catalog

Every reusable thing you've built, with a definition of "complete."

  • Auth: login, reset, email automation
  • Legal/policy pages (mobile vs. financial variants)
  • SEO package · GEO package
  • A manifest — every file it takes to be whole

The catalog points to your real code where it already lives — it never copies it. No duplicate repository, no broken links, no second version to keep in sync.

Autopilot · loop A

You launch it once. After that it runs on a schedule and on triggers, and only talks to you when something's wrong.

Watch

deterministic · ~free

Detect change

Diffs reality against the map. Nothing new? It stops here and costs almost nothing.

cheap model · ~free

Catalog it

A new site or package gets mapped and, for packages, its completeness manifest drafted.

cheap model

Report exceptions only

A short digest: "new subdomain found, not backed up" · "cert expires in 12 days." You review the few things that matter — not the runs.

Autopilot · the interface

How your other agents find it — the "talkative" part

Your build-agents don't need to know where anything is. Atlas exposes the map over MCP — the standard channel one agent uses to query another's knowledge. Two things make reuse automatic:

  • One standing rule in every build-agent: "Before building anything, ask Atlas if we already have it." It becomes a reflex, not a decision.
  • A query channel: the agent asks atlas.search("login + password reset") and gets back the package, its location, its manifest, and the skill to drop it in — complete. No match? It builds fresh, and the watcher catalogs the result.

A second, even simpler path: the map's top-level INDEX.md can load as ambient context (like a CLAUDE.md), so lightweight agents get the lay of the land for free.

Where it lives

Stored as text, in git — not a database

The whole map is plain, human- and AI-readable files in one private git repo. It's the "better .md" you pictured — with superpowers: diffable history is what makes drift detection possible, and there's no second system to maintain.

# atlas/ — one private repo, the single source of truth INDEX.md # the map an agent loads first inventory/ # one file per server packages/ # one file per reusable package + manifest skills/ # the "clone this correctly" recipes # a package entry — points to source, never copies it - id: auth-core source: git@…/shared/auth # real code stays put includes: [login, password_reset, email_templates, sessions] requires: [db: users table, env: SMTP_*] # the parts that go missing variants: [standard, financial(enhanced-security)] skill: skills/apply-auth-core.md

Recommendation

Is it worth it — and is it actually faster?

Verdict · Yes, after break-even

Build it — but let it earn as it grows, never hoard.

There's a real upfront cost: the engine, plus cataloguing your first packages. After that, manual work is near-zero and every reuse is pure gain. Because you rebuild each feature ~five times today, break-even comes fast — a handful of reuses and it's net positive.

Two disciplines keep it honest: the library grows only on real demand (no "huge inventory for nothing," web-scouting is opt-in and approved), and the promote-step must always run — which is exactly the job the autopilot takes off your plate.
